# 阶段 3 第 2 子阶段技术开发文档｜v0.5 可信销售周报（P0）

> 配套文档：PRD v0.5、《通用技术栈手册》、阶段3-M3/M3.1 文档、《前端技术适配声明》。
> 本阶段实现 PRD v0.5 的 P0-1~P0-3；P1（本地口径预设）不在本阶段（PRD §6 建议 P0 真实样表验收后再排期）。真实模型冒烟、真实样表、样例打分放最后统一做。

## 一、阶段目标

把 WorkMate 从"拿到表直接算"升级为"**先确认口径、再计算，结论可回查**"：

- **P0-1 数据检查与字段确认**：生成前展示全表质量、字段映射、A/B 金额口径，阻断不明确输入。
- **P0-2 明确周范围与比较**：用户确认报告周与对比周、两周完整性，不完整/无日期不出误导性环比。
- **P0-3 事实卡与依据回查**：报告每个关键数字可回到来源列、时间段、计算式；`analysis_basis.json` 保存口径与核对结果。

**阶段产物**：多步向导式本地网页（选表 → 检查/确认 → 选周 → 生成 → 结果含事实卡与依据）+ 后端数据检查/口径/周范围/依据模块 + `analysis_basis.json`。

**验收标准**：PRD v0.5 §7.1 的 7 条可重复功能验收；§7.2 真实使用验收放最后。

**明确不做**：P1 口径预设、PPT、跨文件拼接、多工作表合并、自由问答、自动归因/预测、多人登录、云端数据源。

## 二、技术适配摘要

## 六、数据、资产与状态

- **`analysis_basis.json`**（schema_version=1，落 `outputs/<task_id>/analysis_basis.json`）：
  - `field_mapping`：最终采用的列映射（用户确认后）
  - `amount_mode`：`A`（每行金额）| `B`（整单金额去重）
  - `report_week`：`{start, end, tz}`；`compare_week`：`{start, end}`
  - `completeness`：`{report_confirmed, compare_confirmed}`（用户确认）
  - `exclusions`：`[{reason, count, affected_metrics}]`（任何被排除行都要有数量+原因）
  - `metric_formula_version`：本次指标公式版本（如 `2026-09-28-1`）
  - `verify`：独立核对结果（通过/不一致清单）
  - `source_fingerprint`：原始文件 sha256
- 任务持久化不变（tasks.json/trace.jsonl/app.log）；任务 `result` 增加 `basis` 摘要与 `facts`。

## 七、接口与工具设计

统一错误结构 `{"error":{"code","message"}}`。

### 7.1 数据检查接口

`POST /api/v1/inspect`，请求 `{"file": 文件名}`（文件须已在 data/ 内）。响应：

```json
{
  "summary": {"rows": 1500, "columns": ["..."], "file_size": 0, "fingerprint": "sha256..."},
  "mapping": {"sales": "销售额", "date": "日期", "product": null, "channel": null, "order": null},
  "ambiguities": ["存在多个疑似销售额列：金额、成交额，请手动确认"],
  "quality": {
    "sales": {"valid": 1499, "empty": 0, "unparseable": 1},
    "date": {"valid": 1500, "empty": 0, "unparseable": 0},
    "order_complete_rate": 0.98, "duplicate_orders": 12
  },
  "pii_columns": ["客户姓名", "电话"],
  "preview": [{"列": "…", "示例": "…"}],  // 只含参与计算字段，PII 列不显示原值
  "blockers": ["销售额列有 1 个无法解析的值", "金额口径未确认"],
  "weeks": [{"start":"2026-09-07","end":"2026-09-13","has_data":true}, ...],
  "has_date": true
}
```

**规则**：全表统计（非仅预览）；字段识别有歧义时 `ambiguities` 非空且不擅自选定；PII 列（姓名/电话/邮箱/地址等）不进 `preview` 原值。

### 7.2 生成接口（扩展）

`POST /api/v1/tasks`，请求新增字段：

```json
{
  "file": "sales.xlsx",
  "instruction": "做成销售周报",
  "field_mapping": {"sales":"销售额","date":"日期","product":"商品","channel":"渠道","order":"订单号"},
  "amount_mode": "A",
  "report_week": "2026-09-14",   // 该周周一，YYYY-MM-DD；无日期时省略
  "compare_week": "2026-09-07",
  "complete": {"report": true, "compare": true}
}
```

- `amount_mode` 缺失或为 `null` 且存在金额时 → 阻断（`AMOUNT_MODE_REQUIRED`）。
- 无 `date` 映射 → 走"销售数据汇总"模式，产物标题为"销售数据汇总"，不出现"本周/环比/趋势"。

### 7.3 结果与依据接口

- `GET /api/v1/tasks/{id}/basis` → `analysis_basis.json` 内容。
- `GET /api/v1/tasks/{id}/facts` → `{"facts":[...], "change_facts":[...]}`。
- 现有 `report`/`files` 接口不变。

## 八、金额口径算法（F2，核心）

**A 每行金额相加**：总销售额 = 选定销售额列有效值之和（沿用 v0.4 的异常值报错）。商品/渠道/日趋势按行汇总。

**B 整单金额去重**：
- 前置：每行订单号完整（非空），否则阻断金额计算（`B_REQUIRES_ORDER_ID`）。
- 每个订单号的金额只计一次；同一订单号多行金额**不一致** → 阻断（`ORDER_AMOUNT_CONFLICT`，附涉及订单数，不打印原值）。
- 同一订单跨多个日期/渠道且无法确定归属 → 日期趋势、周比较、渠道占比分别标"口径待确认"，不得重复计入。
- 商品金额排名：B 模式无法可靠分摊到商品 → **不生成商品金额排名**。
- 订单量、客单价沿用 v0.4（去重订单量；分母为 0 或未知不计算）。

**负数/多币种**：负数按原表计入并提示数量；同统计范围出现多币种 → 阻断跨币种总额与占比。

## 九、周范围算法（F3）

- 自然周 = 周一 00:00 至下周一 00:00（本机时区）。报告周默认 = 数据中最近有记录的自然周；用户可选。
- 对比周 = 报告周**紧邻**的前一自然周，不跳过空周。
- 环比仅在：两周金额可计算、日期可归属、口径一致、用户分别确认完整、前一周金额 ≠ 0 时给出；否则写"环比暂不可用 + 具体原因"。
- 无日期列 → "销售数据汇总"模式（标题、文案、图表相应调整；总额/订单量仍按全表口径）。

## 十、事实卡与依据（F4）

事实卡结构（每张卡）：

```json
{"id":"total_sales","label":"报告周总销售额","value":20615.49,"unit":"元",
 "source_col":"销售额","formula":"sum(销售额) where 报告周内","range":"2026-09-14~09-20",
 "excluded":0,"verified":true}
```

- 卡集合：报告周总销售额、明细行数、订单量、客单价、环比（可用时）、Top5 商品、渠道占比。
- 变化事实 ≤3 条，由确定性代码计算（如"渠道 A 比上周减少 X，约占总降幅 Y%"），仅当总变化≠0、分类可完整覆盖、方向一致时给贡献百分比，否则只列绝对变化。
- **总结 Prompt 改为只基于事实卡写 ≤200 字**，每个含数字的结论关联卡片编号；无支持事实则不写"建议"。模型不改数字。

## 十一、Prompt 设计

`SUMMARY_SYSTEM` 改为：输入为"已核对的事实卡 JSON"；要求：①只用事实卡数字，禁止自造；②每个含数字结论标注卡片编号（如 [F1]）；③≤200 字，先结论后数据；④没有依据不写建议/原因；⑤内容审核失败保守降级并标"需人工复核"。

## 十二、测试要求（pytest，新增）

1. **A/B 口径**：PRD §7.1 例 1（订单 A 两行各 100 + 订单 B 50 → B 模式总额 150/订单 2/客单 75，A 模式总额 250）；B 订单金额不一致、B 缺订单号 → 阻断。
2. **周比较**：§7.1 例 3（有第 1、3 周缺第 2 周 → 对比周必须是第 2 周，不拿第 1 周）；只有一周/未确认/前一周 0 → 分别给准确不可用原因。
3. **无日期/缺分类**：§7.1 例 4（无日期→"销售数据汇总"；缺商品/渠道→只缺对应图）。
4. **质量计数全表**：§7.1 例 5（1500 行第 1200 行非法金额 → 全表报错阻断）。
5. **依据一致**：§7.1 例 6（report/网页/图表/汇总表与 analysis_basis.json 一致；独立核对注入错误→任务失败）。
6. **安全恢复**：§7.1 例 7（原始文件 sha256 不变；日志/模型输入不含客户信息）。
7. 既有 49 条测试全数保持通过。
