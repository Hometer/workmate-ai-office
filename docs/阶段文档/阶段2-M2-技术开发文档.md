# 阶段 2 第 2 子阶段技术开发文档｜M2 硬化

> 配套文档：PRD v0.3、《通用技术栈手册》V2.1、《技术适配声明》、阶段2-M1 技术开发文档。
> 本文档只覆盖 M2 硬化。真实模型冒烟统一放到最后（与产品经理约定）；本地网页 UI 属 M3。

## 一、阶段目标

- **交付范围（对齐 PRD §8.2 M2）**：在 M1 骨架上增量补 5 项硬化：
  1. 权限目录白名单（只读授权目录、只写成品目录）
  2. 覆盖确认（写已有文件须二次确认）
  3. `verify_metrics` 数字自动核对（s17 目标闭环）
  4. `safety_check` 内容审核（s04 钩子）
  5. 日志系统（每步耗时、权限拦截、审核/核对结果）
- **阶段产物**：M1 CLI 程序升级为"自动核对 + 内容审核 + 权限约束 + 日志"的硬化版。
- **验收标准（PRD §8.2 M2）**：
  1. **数字核对一致率 100%**：`verify_metrics` 自动核对，不一致即任务失败，绝不交付错误数字。
  2. **误删/越权为 0**：只读授权目录、只写成品目录、不覆盖已有文件、原始文件永不改动。
  3. 内容审核不过自动重写 ≤3 次，仍失败交付"保守模板 + 提示人工复核"。
  4. 日志记录每步耗时、权限拦截、审核/核对结果；**不记个人信息、密钥、整表数据**。
- **明确不做**：本地网页 UI（M3）、真实模型冒烟（最后统一做）、PPT（二期）、自由任务规划。
- **主链路片段**：M1 主链路不变，插入两处钩子——`compute_metrics` 后接 `verify_metrics` 核对，`write_summary` 后接 `safety_check` 审核；全程权限白名单 + 日志。

## 二、技术适配摘要

- 沿用《技术适配声明》结论：后端先行、本地优先、数据不出本机。
- 本阶段启用按需模块：`verify_metrics`（s17）、`safety_check`（s04）、目录白名单与覆盖确认（s03）、日志。
- 本阶段偏离/暂缓：数据库、SSE、FastAPI 仍不引入（同 M1，M3 再挂 FastAPI）。

## 六、数据、资产与状态

- 持久化方式不变：`tasks.json`（任务状态）+ `trace.jsonl`（结构化轨迹）+ **`app.log`（人读日志，本阶段新增）**，均带 schema 版本（升到 2）。
- 状态机不变：任务 `created → running → done | failed`；步骤清单新增 `verify_metrics`、`safety_check`。
- 日志边界：只记文件名、行数、耗时、状态、错误类型；**不记单元格值、不记个人信息的完整原文**。

## 七、工具设计（本阶段新增/修改）

统一错误结构 `{"error": {"code", "message"}}`。

| 工具/能力 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| `verify_metrics` | 源文件路径 + 列映射 + 待核对 metrics | 不一致清单（空 = 通过） | 重新读源文件→独立重算→逐项比对；不一致抛 `VERIFY_FAILED` |
| `safety_check` | 总结文本 + metrics | `{pass, reasons}` | 非空、≤800 字、无占位/编造标记、金额型数字须来自 metrics |
| `write_file` | 路径 + 内容 + overwrite | 写入确认 | 只写成品目录；命中已有文件且未 overwrite 抛 `FILE_EXISTS`；永不覆盖原始文件 |
| 读权限白名单（loop 层） | 文件路径 | 放行 / `PERMISSION_DENIED` | 输入文件必须在 `data/` 内 |

**verify_metrics 判定口径**：对 `total_sales / order_count / avg_order_value / mom_growth / top5 / channel_share` 逐项重算比对，数值用容差 `1e-6`，列表按名称+数值比对。任何一项不一致 → 任务失败，不落盘交付。

**safety_check 判定口径**（防编造数字，降低误报）：
- 非空、长度 ≤ 800、不含占位词（如 `mock`、`[TODO]`、`待生成`、`编造`）。
- 提取总结中的数字，仅对"金额型"数字（绝对值 ≥100 或含小数）做来源校验：必须与 metrics 中的某个已知值在 0.1% 容差内匹配，否则判为疑似编造。
- 例：`Top5`、`3个渠道` 这类小整数不误报；`6,358.51`、`43.58%`、`-77.75%` 必须能对应到 metrics。

## 八、Prompt 设计

沿用 M1 的 `SUMMARY_SYSTEM`，按"格式约束三件套"补**正反例**：

- 正例：`本周总销售额 20,615.49 元，环比 -77.75%，Top5 商品为……，建议关注直播渠道。`
- 反例（禁止）：`总销售额大约两万元（不许给约数或自造数字）`；`同比上涨 30%（表里没有的指标）`。

约束句新增：`只能用给你的数字；拿不准的指标写"本表无此数据"，禁止自造约数、百分比或趋势。`

## 十、测试要求

**第一层 mock 测试（pytest，每次开发完必跑）**：
1. `verify_metrics`：正确数据返回空清单；篡改 total_sales / top5 / channel 后返回对应不一致项。
2. `safety_check`：干净总结通过；含编造金额（如 "25000.00"）不过；空/超长不过；含占位词不过；`Top5`/小整数不误报。
3. 权限：读目录外文件抛 `PERMISSION_DENIED`；写目录外抛 `WRITE_FORBIDDEN`；覆盖已有文件无 `--force` 抛 `FILE_EXISTS`；`--force` 后可覆盖；原始文件永不覆盖。
4. 端到端（mock 模型）：完整链路（含 verify + safety）跑通，产出与 M1 一致；数字核对通过。
5. 日志：跑完后 `app.log` 存在，含步骤与耗时，不含单元格值。

**第二层真实冒烟**：放到最后统一做（装 Ollama 后），本阶段如实标注"待验"。
